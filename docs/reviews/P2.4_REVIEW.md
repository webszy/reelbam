## C. Findings

### F01 — P0：恢复后的新 Attempt 可在 queued 状态提交，deadline 随后错误返还

- **位置：** [engine.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/engine.ts:126)（126、346、578 行）；[return.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/credits/return.ts:597)。
- **实际证据：** confirmed-absent 分支先创建下一条 `not_submitted` attempt，再把 generation 改成 queued；下次 `submitStep` 发现已有 attempt，跳过 `openAttempt`，没有先转为 submitting。queued deadline 返还分支不检查已 dispatch/unknown/accepted 的 attempt。
- **故障场景：** 第一次提交 unknown → 恢复确认不存在 → 创建 Attempt 2 → Attempt 2 被 Mock 接受 → 保存 request ID 前中断 → Cron 超过 deadline。
- **实测 R05：** Provider 返回了 Attempt 2 的稳定 job ID；中断时 D1 generation 仍为 queued；deadline 后变为 failed，余额由扣费后的 **4 恢复为 10**。第二次提交本身是合法的新 Attempt；问题是对已接单、未确认失败的任务返还，不是已经证明真实上游发生重复计费。
- **影响：** 提交未知任务被错误判为明确失败，返还已用于接单任务的积分，破坏失败结算的事实前提。本轮只使用 0 成本 Mock，没有真实费用。
- **最小修复：** 对已有新 attempt 的 queued → submitting 与领取做同批围栏，在任何 dispatch 前成立；替换 attempt 和状态变更避免中断不一致。queued deadline 的返还 SQL 再校验不存在未解决的 dispatch/unknown/accepted；发现不一致进入 needs_review，不返还。
- **回归：** 固化 R05；覆盖第二次 Submit 接受前后中断、deadline 并发、已持久化 unknown，以及最后一次 confirmed-absent 的唯一结算。

### F02 — P1：中间状态推进不检查当前 Attempt 租约，并允许恢复状态倒退

- **位置：** [durable.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/durable.ts:357)；[engine.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/engine.ts:240)（240、434 行）。
- **实际证据：** `advanceGeneration` 只核对 user/status/version 和非终态，没有 attempt ID、最新 attempt、owner/token/期限或合法事件。`persistAccepted` 在保存 accepted 后重读任意当前非终态，再改成 processing；轮询完成后的推进同样不带 attempt fence。
- **故障场景与实测：** R03 暂停 A 的 getStatus，时间超过租约后 B 成功领取；恢复 A 后，B 仍持有 token，A 却成功把 processing 推到 storing 并 ack。R04 暂停 A 于 accepted 落库后，让 B 恢复并推进到 storing；A 恢复后把 **storing 改回 processing**。
- **影响：** 租约不再限定状态写入权；重复轮询、阶段倒退和人工审核被迟到结果干扰。已验证的终态 SQL 仍阻止 succeeded/failed 覆盖，因此本项不夸大为已复现终态覆盖。
- **最小修复：** 将相关 attempt 和 generation 推进组合进同一 fenced batch；验证最新 attempt、租约和合法原状态/事件，禁止 accepted 恢复覆盖 storing。跨 I/O 后刷新时间并处理租约失效，不能沿用消息开始时的 now；遇 conflict 必须停止后续推进。
- **回归：** 固化 R03/R04，增加 Submit/Poll/R2 I/O 暂停后接管、needs_review 竞争、旧 attempt 和成功/失败终态竞争。

### F03 — P1：任务失败或停机待审后 Outbox 仍可无限发送

- **位置：** [engine.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/engine.ts:78)（78、108、425 行）；[dispatch.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/dispatch.ts:86)；[rows.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/rows.ts:54)。
- **实际证据：** terminal/needs_review 消息直接 ack；provider_failed 结算没有结束 poll Outbox。发送次数上限只在 Queue send 抛错时检查，send 成功永远释放回 pending。调度查询不排除已终止/待审 generation，按最老 created_at 限取 20 条。
- **故障场景：** 一次 Provider 明确失败后不断运行 Cron；Queue 每次成功接收并 ack 同一无用消息。
- **实测 R01：** generation 已 failed，追加 10 轮发送全部成功，poll Outbox 仍 pending，`delivery_attempt_count=12`，超过默认上限 8。
- **影响：** 消息和数据库工作无法收敛；最旧无用事件持续占用调度窗口，可能挤占新任务恢复容量。容量影响由查询顺序推得，未用 20 个生产 consumer 验证。
- **最小修复：** 终态、needs_review 和过时消息有持久化的结束/停放流程；确认持久状态后关闭对应 Outbox。对长期“发送成功但没有业务推进”的事件设独立预算和审计，不能只限制 send 异常次数。
- **回归：** failed/succeeded/needs_review/旧 attempt 重放后不再发送；重复 send 仍安全；20 条旧事件不饿死新任务。

### F04 — P1：首条 Outbox 进入 dead 后，deadline 无法结算 queued 任务

- **位置：** [maintenance.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/maintenance.ts:24)；[engine.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/engine.ts:578)；[rows.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/rows.ts:42)。
- **实际证据：** 超过 deadline 的 maintenance 分支直接调用 handler 后 continue；`settleDeadline` 必须找到 pending/leased start_submission 才能领取并返还；dead 不在读取范围内，也不会在这条分支补建事件。
- **故障场景：** Queue 连续发送失败 8 次，首条 Outbox 变 dead；Cron 中断一段时间，在 deadline 后恢复。
- **实测 R09：** 连续运行 3 次 deadline 后维护，仍 **queued、余额 4、唯一 Outbox dead/attempts=8**，没有 Provider attempt 或失败结算。
- **影响：** 未提交任务永久卡死，已扣积分被占用；继续运行同样的 Cron 无法自愈。
- **最小修复：** deadline 处理本身有独立于 Queue 可达性的持久化领取/恢复路径，可安全处理 dead 首事件，同时保留 F01 的未提交事实检查和单次返还。
- **回归：** 所有 start Outbox dead、delivered 或缺失时，在 deadline 前后分别恢复；与并发 submit/settlement 竞争仍只有一个合法结果。

### F05 — P1：storing 绕过 deadline，持久存储故障会无限重试

- **位置：** [engine.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/engine.ts:105)（105、457 行）；[maintenance.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/maintenance.ts:24)；[protocol.ts](/Volumes/Development/Workspace/reelbam/packages/data/src/video/protocol.ts:37)。
- **实际证据：** handler 和 Cron 都把 storing 排除在 deadline 外。限制只有 submit/poll/outbox 次数，没有跨消息的 storage 次数或 storage deadline；R2 put/head 异常继续 retry，dead 事件又可被新建，DLQ 也只补存储事件。
- **故障场景与实测 R06：** R2 持续不可用，时钟推进到创建后两小时以上；11 次 put 失败后任务仍 storing，既未停放也没有存储预算耗尽审计。
- **影响：** 任务永久占用积分和维护窗口；active 查询固定取最旧 20 条且无扫描游标，长期 storing 还可能阻挡其他丢消息任务的维护。
- **最小修复：** 持久化存储尝试预算/截止时间，采用有上限的退避；耗尽后 needs_review 并保留已有对象登记信息，禁止重新 Submit。让维护扫描能越过长期异常任务。瞬时 R2 故障不能直接当作 Provider 明确失败退款。
- **回归：** put/head/D1 登记持续故障、旧租约临时对象、deadline 后恢复，以及超过 20 条异常任务时的新任务恢复。

### F06 — P1：已提交请求的幂等重放依赖当前路由和素材状态

- **位置：** [create-generation.ts](/Volumes/Development/Workspace/reelbam/server/services/video/create-generation.ts:60)（60、72、85、89 行的处理顺序）。
- **实际证据：** 在读取 `(userId,idempotencyKey)` 前，先校验 deadline/quote、选择当前路由并重新检查素材 availability。
- **故障场景与实测 R02：** 首次创建成功但调用方丢失响应；禁用原路由后使用相同 key/input 重试。返回 `no_compatible_route`，没有返回已存在的 generation。余额仍为 4，没有重复扣费。
- **影响：** 任务已经接受，调用方却收到创建失败；客户端若据此换 key，可能另建任务。素材过期/当前能力变化也有相同的静态风险，本轮未逐一动态注入。
- **最小修复：** 完成身份、key 和纯输入结构/规范化后先查原任务；同 hash 返回原结果，不重新要求当前路由、价格、素材可用或新 deadline。仅新 key 走创建时业务校验。
- **回归：** 提交响应丢失后禁用/更换路由、改变能力、价格或素材状态；同 key 不同合法输入仍冲突，不能追加任务。
